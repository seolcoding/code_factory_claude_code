# GitHub 이슈 해결 계획 수립

다음 프로세스를 따라 GitHub 이슈를 분석하고 해결 계획을 수립해주세요:

**이슈 번호:** $ARGUMENT

## 1단계: 이슈 정보 수집

먼저 `gh` CLI를 사용하여 이슈 정보를 가져오세요:

```bash
# 이슈 상세 정보 가져오기
gh issue view $ARGUMENT

# 이슈 댓글 가져오기 (추가 컨텍스트)
gh issue view $ARGUMENT --comments
```

수집할 정보:
- 이슈 제목
- 이슈 본문 (설명, 재현 방법, 예상/실제 동작)
- 레이블 (bug, enhancement, documentation 등)
- 담당자 및 마일스톤
- 관련 댓글 및 추가 컨텍스트

## 2단계: 이슈 분석

수집한 정보를 바탕으로 다음을 분석하세요:

### 문제 유형 식별
- **버그**: 기존 기능의 오작동
- **기능 추가**: 새로운 기능 요청
- **개선**: 기존 기능의 성능/UX 개선
- **문서**: 문서 추가/수정
- **리팩토링**: 코드 구조 개선

### 영향 범위 파악
- 영향받는 파일/모듈 식별
- 관련 의존성 확인
- 기존 테스트 영향도 평가

### 근본 원인 분석 (버그인 경우)
- 재현 단계 확인
- 예상 원인 추론
- 관련 코드 영역 식별

## 3단계: 코드베이스 조사

이슈 해결에 필요한 코드를 조사하세요:

1. **관련 파일 검색**
   - Grep, Glob 도구를 사용하여 관련 코드 찾기
   - 필요시 Task 도구로 Explore 에이전트 사용

2. **현재 구현 이해**
   - 관련 파일 읽기
   - 기존 로직 파악
   - 테스트 코드 확인

3. **의존성 분석**
   - 변경이 필요한 파일 목록
   - 영향받을 수 있는 다른 기능

## 4단계: 해결 계획 수립

다음 형식으로 상세한 해결 계획을 작성하세요:

### 해결 방법 요약
- 접근 방법 설명 (1-2문장)
- 주요 변경 사항 개요

### 세부 작업 목록

각 작업에 대해 다음 정보를 포함:

```
1. [작업명]
   - 파일: [변경할 파일 경로]
   - 내용: [구체적인 변경 내용]
   - 예상 시간: [시간]
   - 완료 조건: [검증 방법]

2. [작업명]
   ...
```

### 작업 우선순위 및 순서

```
Phase 1 (병렬 가능):
  - 작업 A
  - 작업 B

Phase 2 (Phase 1 완료 후):
  - 작업 C

Phase 3 (최종):
  - 작업 D (통합 테스트)
```

### 테스트 계획

**단위 테스트:**
- [ ] 새로운 함수/컴포넌트 테스트
- [ ] 기존 테스트 수정/추가
- [ ] 엣지 케이스 테스트

**통합 테스트:**
- [ ] 모듈 간 연동 테스트
- [ ] E2E 시나리오 테스트

**수동 테스트:**
- [ ] 이슈에 명시된 재현 단계 확인
- [ ] UI/UX 확인 (해당하는 경우)
- [ ] 브라우저/디바이스 호환성 (해당하는 경우)

### 잠재적 리스크

- **리스크 1**: [설명]
  - 완화 방안: [대책]

- **리스크 2**: [설명]
  - 완화 방안: [대책]

### 롤백 계획

만약 문제가 발생할 경우:
1. [롤백 단계 1]
2. [롤백 단계 2]

## 5단계: 검증 체크리스트

작업 완료 후 다음을 확인:

```
[ ] 이슈에 명시된 문제가 해결됨
[ ] 새로운 테스트 추가 및 통과
[ ] 기존 테스트 모두 통과
[ ] 코드 스타일/린트 규칙 준수
[ ] 관련 문서 업데이트 (필요시)
[ ] 코드 리뷰 준비 완료
[ ] 커밋 메시지 작성 (이슈 번호 포함)
[ ] PR 생성 및 이슈 링크
```

## 6단계: 사용자 승인 요청

계획 수립이 완료되면 **ExitPlanMode 도구를 사용**하여 사용자에게 계획을 제시하고 승인을 받으세요.

계획 요약에 포함할 내용:
- 이슈 요약
- 해결 방법 개요
- 주요 작업 목록 (3-5개 핵심 항목)
- 예상 소요 시간
- 주요 변경 파일

**중요:** 사용자가 승인한 후에만 실제 코드 작성을 시작하세요!

## 추가 지침

### 버그 수정 시
1. 재현 가능한 테스트 케이스 먼저 작성
2. 테스트가 실패하는 것 확인
3. 버그 수정
4. 테스트 통과 확인
5. 회귀 테스트 실행

### 기능 추가 시
1. 기존 코드와의 일관성 유지
2. 확장 가능한 구조로 설계
3. 문서화 포함
4. 예제/사용법 제공

### 리팩토링 시
1. 기존 테스트 먼저 확인
2. 작은 단위로 점진적 변경
3. 각 단계마다 테스트 통과 확인
4. 성능 영향도 측정

## 예시 출력

```markdown
# Issue #123: 로그인 버튼 클릭 시 에러 발생

## 문제 분석
- 유형: 버그
- 영향 범위: 인증 모듈, 로그인 페이지
- 원인: 비동기 처리 중 에러 핸들링 누락

## 해결 계획

### 접근 방법
로그인 액션에 try-catch 블록 추가 및 에러 상태 UI 표시

### 작업 목록
1. 로그인 액션 에러 핸들링 추가
   - 파일: app/login/actions.ts
   - 내용: submitLogin 함수에 try-catch 추가
   - 예상: 30분

2. 에러 UI 컴포넌트 추가
   - 파일: app/login/page.tsx
   - 내용: 에러 메시지 표시 영역 추가
   - 예상: 20분

3. 테스트 작성
   - 파일: app/login/actions.test.ts
   - 내용: 에러 케이스 단위 테스트
   - 예상: 40분

### 총 예상 시간: 1.5시간

### 테스트 계획
- [ ] 잘못된 자격증명 입력 시 에러 메시지 표시
- [ ] 네트워크 에러 시 적절한 에러 처리
- [ ] 성공 케이스는 여전히 정상 작동

이 계획으로 진행해도 될까요?
```

---

**실행 순서:**
1. gh CLI로 이슈 정보 수집
2. 코드베이스 조사 (Grep, Read, Task 도구 사용)
3. 상세 계획 수립
4. ExitPlanMode로 사용자 승인 요청
5. 승인 후 작업 시작
